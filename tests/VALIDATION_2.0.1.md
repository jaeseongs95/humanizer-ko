# Humanizer KO 2.0.1 검증 기록

## 결론

`계약`, `권위`, `효과`, `경계`는 AI 글을 판별하는 금칙어가 아니라 문맥을 다시 볼 신호다. 일반 산문에서 기능이 확인되고 고정 명칭이 아닐 때만 자연스럽게 고친다. 코드 식별자, 직접 인용, 문서 표제, 링크 라벨, 용어집 항목과 여러 곳에서 반복되는 도메인명은 부분적으로 자동 개명하지 않는다. 뜻이 모호하면 표현을 유지하고 필요한 정의를 확인한다.

이 기준에 따라 다음 세 경우를 분리했다.

| 경우 | 처리 |
| --- | --- |
| 정식 명칭이 아닌 일반 설명이며 기능이 분명함 | 문맥에 맞게 교정 |
| 정상 전문 용어 또는 프로젝트의 고정 명칭 | 유지. 이름을 바꾸려면 전역 일관성 검토를 제안 |
| 뜻이나 명칭 여부가 불분명함 | 보존하고 문맥 확인 |

## 다각도 감사와 논쟁

초기 구현은 `1.0 계약`, `Engine 설치 계약`을 자동 교정하는 사례를 추가했지만, Skill의 고정 명칭 보호 원칙과 충돌했다. 문자열 포함 여부만 보던 검증기는 부정문으로 의미를 뒤집거나 정답 단어를 문장 끝에 덧붙여도 통과했다.

감사와 논쟁은 역할을 분리해 진행했다.

- 언어학·번역 판단: `/root/linguistic_audit`
- 적대적 테스트와 우회 재현: `/root/adversarial_audit`
- 패키지·배포 감사: `/root/release_audit`
- 사용자 의도 반론: `/root/intent_challenger`
- 실제 FlowMarshal 코드·문서 추적: `/root/domain_trace`
- 상충 결론 판정: `/root/debate_judge_2`
- 증거 구조 재설계: `/root/evidence_architect`
- 문서·사례 구현: `/root/docs_implementer`
- 검증기 구현: `/root/checker_implementer`
- 독립 행동 실행과 감사: `/root/forward_runner_3`, `/root/forward_auditor_3`

논쟁에서는 링크 라벨도 기능이 분명하면 바로 고칠 수 있다는 의견과, 실제 문서 표제라면 부분 개명을 막아야 한다는 의견이 맞섰다. 사용자 제공 문서가 `D:\codex\flowmarshal\README.md`와 같은 파일임을 해시로 확인했고, `1.0 계약`, `Engine 설치 계약`, `Goal Contract`, `허용 효과`가 실제 문서 표제·도메인 객체·용어 체계와 연결된 사실을 추적했다. 이 구체적 근거에 따라 해당 명칭은 자동 치환 사례에서 제외하고 전역 용어 정리 대상으로 분류했다. 정식 명칭이 아니라는 전제가 명시된 같은 표현은 일반 산문 교정 사례로 남겼다.

## 행동 검증

[정본 사례](cases/2.0.1.json)에 R01~R04와 T01~T07의 `request`와 편집 대상 `input`을 분리해 고정했다. 의미 보존은 `input`을 기준으로 판정하며 `request`의 지시·배경은 결과에 되풀이할 본문으로 보지 않는다. 의미 조건은 [EVALUATION_PROTOCOL.md](EVALUATION_PROTOCOL.md)에 먼저 기록했다. 정답이나 과거 결과를 받지 않은 `/root/forward_runner_3`가 [실행 결과](evidence/2.0.1/final.json)를 만들고, 별도 에이전트 `/root/forward_auditor_3`가 [감사 결과](evidence/2.0.1/audit.json)를 판정했다.

[HOLDOUT_CASES.md](HOLDOUT_CASES.md)의 H11은 수동 전이 사례이며 이번 해시 결속 실행 세트에는 포함하지 않았다. H11에서 가져온 핵심 대조 조건은 정본 T05에 별도로 구성해 실행·감사했으며, H11 자체를 실행했다고 주장하지 않는다.

첫 최종 배포 감사에서는 `request`와 `input`이 한 문자열에 섞여 배경 설명을 최종문에서 뺀 결과가 사실 누락처럼 해석되는 결함을 발견해 NO-GO로 판정했다. 사례 스키마와 검증기를 분리 구조로 고친 뒤 새 실행자와 감사자로 전체 사례를 다시 검증했다. 과거 schemaVersion 2 기록도 당시 자료 내부의 보호 구간만 검사하고, 현재 Skill·규약·독립 감사와 결속됐다고 오해하지 않도록 출력 범위를 제한했다.

| 사례 | 확인 항목 | 결과 |
| --- | --- | --- |
| R01~R04 | 호출 경계, 사실·인용·코드·URL 보존 | 통과 |
| T01 | 고정 명칭이 아닌 `1.0 계약`, `Engine 설치 계약` 교정 | 통과 |
| T02~T03 | 정상 계약 용례, 직접 인용과 식별자 보호 | 통과 |
| T04·T07 | 뜻이 불분명한 표현의 임의 해석 방지 | 통과 |
| T05 | 일반 산문의 직역만 교정하고 정상 용례·식별자·불명확한 용어 보호 | 통과 |
| T06 | 고정 산출물명·용어집 항목·Markdown 링크의 부분 개명 방지 | 통과 |

실행 기록은 Skill·정본 사례·평가 규약의 LF 정규화 SHA-256을 저장한다. 감사 기록은 실행 파일 전체와 사례별 출력 해시를 다시 묶는다. 자동 검사는 문자 보존과 증거 결속만 확인하며 의미·자연스러움은 독립 감사 결과로 남긴다.

## 한계

이번 검증은 고정한 11개 사례의 단일 독립 실행이다. 모든 모델과 문서 장르에서 같은 결과가 나온다고 보장하지 않는다. `계약`, `권위`, `효과`, `경계`가 AI 글에 더 자주 나온다는 빈도나 AI 탐지 기준도 입증하지 않는다. 프로젝트의 고정 명칭 여부는 해당 코드·용어집·문서 참조를 확인해야 하며, 자동 검사만으로 문장 의미를 판정할 수 없다.
