# 2.0.2 구조 중심 교정 검증 기록

## 확인한 원인

2.0.1은 단어 사전을 변환 엔진으로 쓰지는 않았지만, 행동 검증 사례가 `계약`, `권위`, `효과`, `경계`에 몰려 있었다. 그래서 특정 예시를 잘 처리한다는 결과를 다른 어휘에도 적용되는 구조적 교정의 근거처럼 볼 위험이 있었다. 지침에도 문맥과 기능을 보라는 원칙은 있었으나 다음 판정 절차가 충분히 구체적이지 않았다.

- 명사구에서 행위자·대상·기준·출처·시간·용도를 구분하는 절차
- 행위와 결과물을 나누고 서술어가 요구하는 의미 자리를 확인하는 절차
- 조건 나열의 문법 형식과 논리 범위, 대비의 비교 축을 맞추는 절차
- 앞 문장의 설명·보완·대조가 아닌 별개 원칙을 문단에서 분리하는 절차

따라서 문제를 특정 단어 누락이 아니라 검증의 어휘 편중과 구조 판정 절차의 부족으로 정리했다.

## 구현 방향

25개 패턴 체계는 유지했다. 작업 순서와 패턴 1·6·10·14·18에 의미 역할, 행위·결과물 구별, 서술어 자리, 조건 병렬, 대비 축, 문단 화제 연결을 추가했다. 특정 단어 목록은 변환 규칙으로 쓰지 않으며, 후보를 찾는 보조 신호로만 사용할 수 있다. 고정 명칭·식별자·전문 용어와 뜻이 불명확한 표현은 이전과 같이 보호한다.

검증기는 다음 실패를 실행 계층에서 거부한다.

- 2.0.1의 실행·감사를 2.0.2 결과로 다시 제출
- 실행자와 감사자가 같음
- Skill, README, 행동 사례, 사례 정본, 평가 규약, 전이 동결 기록, 실행 출력 또는 감사 결과의 해시 불일치
- 새 어근이 동결 전 구현·개발 자료에 이미 있거나 실제 전이 입력에 없음
- 전이 어휘군에 교정·정상·고정명·모호 사례 중 하나가 빠짐
- 개발 최소대립쌍의 원문이 유니코드·줄바꿈·공백 정규화 뒤 서로 다름
- 핵심 감사 축을 `notApplicable`로 생략하거나 대조 사례의 `pairwiseContrast`가 `pass`가 아님

## 독립 검토와 논쟁

구현 전에 언어 규칙, 평가 설계, 일반화 위험, 릴리스 범위 관점을 분리해 검토했다. 별도 판정자는 25개 패턴을 유지하면서 구조 규칙을 보강하고, 기존 11개 회귀 사례와 사용자 최소대립 2개, 동결 후 새 어휘 전이 4개를 한 번의 독립 실행과 별도 감사로 검증하는 안을 채택했다. 사전형 치환표, 세 차례 반복 실행과 감사자 두 명은 이번 패치의 필수 범위에서 제외했다.

검증기 공격 검토에서는 선언 어근과 실제 입력의 불일치, 공백을 이용한 최소대립 분리, 핵심 감사 축의 `notApplicable` 우회를 발견했다. 세 경로를 차단하는 코드와 음성 테스트를 추가했다.

## 전이 사례와 실행 분리

`/root/evaluation_design/fresh_holdout_author`는 이전 대화·README·테스트·평가 규약·과거 결과를 받지 않고 `SKILL.md`만 읽어 `환류` 어휘군의 X01–X04를 작성했다. 이 어근은 동결 전 Skill·README·개발 사례에 없었다.

- X01은 일반 설명의 행위·결과물 자리 불일치를 고친다.
- X02는 같은 어근의 자연스러운 일반 용례를 유지한다.
- X03은 같은 어근이 든 정식 행사명을 보존한다.
- X04는 뜻과 명칭 지위가 불명확해 확인을 요청한다.

첫 두 예비 실행은 정본 증거로 채택하지 않았다. 첫 실행은 초안과 최종본에서 보호 문자열을 반복했고, 두 번째 실행은 날짜를 복제하고 반복된 버전 문자열을 줄여 자동 보존 조건을 통과하지 못했다. 합격 기준이나 출력을 사후 수정하지 않고 두 실행을 폐기했다.

최종 실행자 `/root/evaluation_design/fresh_behavior_runner_3`는 Skill과 사례 정본만 읽고 17개 결과를 만들었다. 보호 문자열 자동 검사를 통과한 이 실행만 `tests/evidence/2.0.2/final.json`에 결속했다. 실행 결과나 선호 판정을 받지 않은 감사자 `/root/generalization_auditor/fresh_behavior_auditor_202`가 고정 평가 규약에 따라 17개 사례와 다섯 판정 축을 확인했다. 감사 결과는 모두 `pass`였고 `tests/evidence/2.0.2/audit.json`에 실행 전체와 각 출력의 해시를 묶었다.

## 검증 결과

- 행동 정본·보호 문자열·독립 감사 결속: 87개 통과
- 패키지 검사: v2.0.2, 패턴 25개, 라이선스와 제3자 고지 통과
- 검증기 테스트: 45개 통과
- Codex Skill 빠른 검사와 플러그인 manifest 검사 통과
- `skills@1.5.20 add . --list`에서 `humanizer-ko` 탐색 확인
- 사례 수: 회귀 11개, 사용자 개발 최소대립 2개, 동결 후 전이 4개
- 전이 최소대립: 교정·정상·고정명·모호 역할 각각 1개
- 독립 감사: 17개 사례 전체 `pass`

실행·감사 근거는 다음 파일에 있다.

- `tests/evidence/2.0.2/freeze.json`
- `tests/evidence/2.0.2/final.json`
- `tests/evidence/2.0.2/audit.json`

로컬 환경에는 실제 Python 대신 Windows Store 자리표시자만 있어 Codex 번들 Python으로 Python 검사를 실행했다. `npx` 대신 같은 패키지 버전의 `pnpm dlx`를 사용했다. 로컬에는 Claude CLI가 없어 두 Claude manifest 명령은 실행하지 못했으며, 공개 전 GitHub Actions에서 해당 검사를 확인한다.

## 한계

채택한 정본 실행은 한 번이고 감사자는 한 명이다. 동결 뒤 선정한 `환류` 한 어휘군에서 구조적 구별을 관측했으므로, 반복 실행 안정성이나 모든 어휘·모델에 대한 일반화를 입증하지 않는다. 기존 네 단어 사례는 회귀 방지에만 사용했으며 새 어휘 전이 점수로 세지 않았다.
